Documenting a plugin

A plugin carries its own record: a README, the decisions that shaped it and the prompts it was built with. Copy the two templates below, fill them in and keep them with the plugin.

1

What a plugin ships

oaken_plugins/triager_kev/
  __init__.py          the plugin: docstring, kind, name, tags, config model
  docs/
    README.md          what it is for, its settings, an example, known limits
    decisions/         why it works this way: one decision per file
      0001-short-title.md
    prompts/           the prompts it was built with, in order
      01-short-name.md

In oaken-plugins the folder sits in the plugin's subpackage. In your own package it sits beside pyproject.toml. The settings and commands of a plugin document themselves (plugin describe), so the README does not repeat them. These pages and Writing a plugin are the public documentation. A plugin's docs/ is its internal record.

Write a decision when you choose between options a later reader would otherwise reopen: a rule's finality, what counts as confidential, which library. Never edit an accepted decision's text: a change is a new decision that supersedes it. Write a prompt for any job an agent did, so the work can be reproduced. Say in its first line that AI wrote it and whether a person has reviewed it.

2

The decision template

Decisions use MADR. Number the files 0001-, 0002- within the plugin.

---
status: proposed
date: YYYY-MM-DD
decision-makers: the people who decided
---

# The decision, as a short title

## Context and Problem Statement

The situation and the question that needs an answer, in two or three sentences.

## Decision Drivers

* a force or concern that shapes the choice
* another one

## Considered Options

* option one
* option two
* option three

## Decision Outcome

Chosen option: "option one", because it meets the drivers best (say how).

### Consequences

* Good, because …
* Bad, because …

### Confirmation

How the team will know the decision was carried out (a review, a test, a check).

## Pros and Cons of the Options

### option one

* Good, because …
* Bad, because …

### option two

* Good, because …
* Bad, because …

## More Information

Links, related decisions, and when to revisit this one.

---

This layout follows MADR, Markdown Architectural Decision Records (https://adr.github.io/madr/). `adr-index.py`
reads the `status:` line; `adr-check.py` checks only that a status is present.

The prompt template

One prompt, one job. Number the files in the order they were run.

# Title: the job, as a short sentence

<!-- Copy this file to prompts/NN-short-name.md. One prompt, one job. Delete these comments. -->

AI-generated, unreviewed by a human. <!-- Drop this line once a person has read it. -->

## Context

Who is asking and why, in two or three sentences. The model, the tool and the date it was written with. What it
builds on (a repository, a commit, an ADR by number). Anything an agent starting cold must know.

## Goal

The outcome, in one or two sentences. State what is true when the job is done, not the steps.

## Read first

- the files, docs and ADRs to read before touching anything (paths, not summaries)
- the decisions that are settled. Say "do not reopen them".

## Scope

- **In:** what this job changes.
- **Out:** what it must not touch, and what it leaves for a later prompt.

## Constraints

- Smallest complete change. Name what you skipped.
- Every Python file starts with `# SPDX-License-Identifier: Apache-2.0`.
- Tests use synthetic data, never the network, a model server or real content.
- Do not commit or push. The owner confirms the provenance trailer first.
- <!-- the constraints specific to this job: versions, files, interfaces that must not change -->

## Steps

1. A step an agent can do and check. Name the test or command that shows it worked.
2. The next step.

## Done when

- [ ] the checks that must pass (`tools/QA.sh`, a named test)
- [ ] the docs that must change with the code
- [ ] the ADR written or amended, if a decision was made

## Questions

Put open questions in one block at the end: numbered, one bold line each, your default beside it.

## Report back

What changed, what you skipped, what you did not verify, and any risk the owner must know.
